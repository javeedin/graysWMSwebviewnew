# CLAUDE.md — Gray's WMS WebView Application

## Project Overview

Gray's WMS (Warehouse Management System) is a **hybrid desktop-web application** built with C#/.NET 8.0 Windows Forms hosting a WebView2 (Chromium) browser control. The web frontend uses vanilla JavaScript with jQuery and DevExtreme components, backed by Oracle APEX REST APIs and Oracle Database.

**Key modules:** Trip Management, Printer Management, Print Job Queue, Monitor Printing, Inventory Management, Receiving, Fusion SQL, and Claude AI Integration.

## Architecture & Key Patterns

### IPC Bridge (C# ↔ JavaScript)

Communication between the C# backend and JavaScript frontend uses WebView2 messaging:

- **JS → C#:** `window.chrome.webview.postMessage(message)` sends a JSON message
- **C# → JS:** `webView.CoreWebView2.ExecuteScriptAsync(...)` calls JS from C#
- **Routing:** `WebViewMessageRouter.cs` dispatches incoming messages by `action` field
- **Callbacks:** `window.pendingRequests[requestId]` stores callback functions keyed by request ID

### SPA Navigation

`index.html` uses `data-page` attributes on menu items. The `showPage()` function in `app.js` hides/shows sections. No client-side router.

### State Management

- **C#:** Stateful service classes (`PrintJobManager._printQueue`, etc.)
- **JavaScript:** Global variables (`currentParams`, `allPrintJobs`, `monitoringTripsData`)
- **Persistence:** JSON files at `C:\fusion\` (printer config, print jobs, orders)

### API Integration

- **Oracle APEX REST:** Base URL in `config.js` → `API_CONFIG.APEX_BASE_URL`
- **Oracle Fusion:** SOAP XML requests via `FusionPdfDownloader.cs`
- **Claude API:** Direct HTTP POST via `ClaudeApiHandler.cs`
- **HTTP Client:** `RestApiClient.cs` with 30-second timeout and async/await

## Important Notes for AI Assistants

1. **Form1.cs is large** (~1800 lines). It is the main orchestrator — read it before making changes to core application flow. `Form1_PrintHandlers.cs` is a partial class extension of Form1.

2. **Web assets must be registered in `.csproj`** — if you add a new `.js`, `.html`, or `.css` file, add a `<None Update="filename">` entry with `CopyToOutputDirectory` so it's included in the build output.

3. **No package manager for frontend** — JavaScript libraries are loaded via CDN `<script>` tags in `index.html`. Do not look for `package.json` or `node_modules`.

4. **Windows-only** — This application requires Windows (WebView2, Windows Forms, Windows printing APIs). Paths use backslashes and `C:\fusion\` is hard-coded for local storage.

5. **Config points to production** — `config.js` contains the production Oracle APEX URL. Be careful when modifying API configuration.

6. **IPC message format** — Messages between JS and C# follow this pattern:
   ```json
   { "action": "actionName", "requestId": "unique-id", "data": { ... } }
   ```
   New actions require handler registration in `WebViewMessageRouter.cs` and corresponding JS code.

7. **Credentials** — Fusion credentials are stored in plain text in local JSON files. Do not introduce additional credential storage without encryption.

8. **Partial class pattern** — `Form1` uses partial classes split across `Form1.cs` and `classes/Form1_PrintHandlers.cs`. Add new Form1 methods in the appropriate partial class file.

9. **Oracle PL/SQL conventions** — REST endpoints use `HTP.p()` for manual JSON construction. New endpoints should follow the numbered script pattern in `apex_sql/`.

29. **DuckDB files are AES-256 encrypted** (`classes/DuckDbVault.cs`; wms2.duckdb and finance.duckdb — Teach Me and the Fusion Model files are not) — one random 256-bit key per PC, DPAPI-protected with machine scope in `%ProgramData%\GraysWMS\duckdb.key` (falls back to `%APPDATA%\GraysWMS\duckdb.key` with user scope when ProgramData is not writable; `GRAYSWMS_DUCKDB_KEYFILE` names another file; on Linux (tests) the key is kept plain in that file), so every Windows user and every WMS window on the PC opens the same file and a copied file or key is useless elsewhere. DuckDB opens an encrypted file only through `ATTACH … (ENCRYPTION_KEY …)` on an in-memory connection: `DuckDbVault.Open(path, readOnly, alias)` = `:memory:` + `Attach` + `USE alias` (unqualified names still mean the file; `information_schema` / `duckdb_tables()` queries filter on the catalog — `Wms2Store.CATALOG` = `wms2`, Finance Lens `fin`), `Attach(conn, alias, path, readOnly)` adds the key when the file is encrypted (probe: a read-only ATTACH without a key fails with "encrypted") or new. **Writing an encrypted file needs DuckDB's OpenSSL crypto = the `httpfs` extension** (the built-in mbedtls only reads; `force_mbedtls_unsafe` is never used): `Prepare(conn)` runs `LOAD httpfs` (DuckDB's own extension folder), else `LOAD` of the copy shipped next to the exe (`dist\duckdb-ext\v{version}\{platform}\httpfs.duckdb_extension`, downloaded by `create-distribution-folder.bat` from extensions.duckdb.org for the DuckDB.NET version in `engine/FusionModel/FusionModel.csproj`), else `INSTALL httpfs` once in the background; until it loads, new files are created plain and plain files stay plain (`CryptoState` unavailable + `CryptoNote`), reads of encrypted files work regardless. **Migration**: the first open of a plain file with the crypto loaded runs `COPY FROM DATABASE old TO new` into `<file>.enc-tmp`, checks every table's row count, `CHECKPOINT`, swaps the files and deletes the plain one (`lastMigration`); a failed migration leaves the plain file in place and is tried again next time. `temp_file_encryption = true` on encrypted attaches (spill files). Every Finance Lens open goes through the vault (`Session` READ_ONLY attach, `OpenWrite`, the direct opens, `CarryOver`'s `prev`, the `finance.new.duckdb` of a Fusion / BICC load — `CopyCurrent` copies the encrypted file as is); `Wms2Store.WithDb` opens through it inside the mutex (a lock error is still retried). `w2Status` and `finStatus` carry `encrypted` / `crypto` / `cryptoNote`; WMS 2.0 › Data & sync shows a lock / "not encrypted yet", Finance › Data & folder an *Encryption* row. `GRAYSWMS_DUCKDB_PLAIN=1` switches encryption off (plain attach, no migration). Performance: block-level AES with hardware acceleration through OpenSSL, 5–10 % on disk-bound work, nothing on cached reads; the DuckDB SQL of the stores is unchanged. Cross-checked in the sandbox with the Python DuckDB 1.5.6 (same engine version as DuckDB.NET.Data.Full 1.5.6): attach / COPY FROM DATABASE / wrong key ("Wrong encryption key used to open the database file") / no key ("Cannot open encrypted database") / read-only attach with the key / catalog-filtered information_schema.
